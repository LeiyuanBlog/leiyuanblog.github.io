## K8s Service网络模型深度解析

#### 为什么写这篇

1. 在上一篇文章中，我们深入探讨了Pod的生命周期。今天我们继续深入，聊一聊Kubernetes中至关重要的Service网络模型
2. Service是K8s中实现服务发现和负载均衡的核心组件，理解它的工作原理对于排查网络问题至关重要！

#### 什么是Service？

在Kubernetes中，Pod是短暂的，它们会被创建、销毁、重新调度。每次Pod重启，IP地址都可能改变。那么问题来了：**如何让客户端稳定地访问这些不断变化的Pod呢？**

答案就是**Service**。Service为一组Pod提供：

- **稳定的虚拟IP（ClusterIP）**
- **DNS名称**
- **负载均衡**

#### Service的四种类型

| 类型 | 说明 | 使用场景 |
| --- | --- | --- |
| ClusterIP | 默认类型，只在集群内部可访问 | 内部服务通信 |
| NodePort | 在每个节点上开放一个端口（30000-32767） | 开发测试、简单外部访问 |
| LoadBalancer | 使用云厂商的负载均衡器 | 生产环境外部访问 |
| ExternalName | 将Service映射到外部DNS名称 | 访问集群外部服务 |

#### Service网络模型核心原理

##### 1. ClusterIP的本质

当你创建一个Service时，K8s会分配一个虚拟IP（ClusterIP）。这个IP：

- 不绑定任何网卡
- 只存在于iptables/IPVS规则中
- 是一个"虚拟"的概念

```yaml
apiVersion: v1
kind: Service
metadata:
  name: my-service
spec:
  selector:
    app: my-app
  ports:
    - port: 80
      targetPort: 8080
  type: ClusterIP
```

##### 2. kube-proxy的角色

kube-proxy是实现Service网络的关键组件，它有三种模式：

**iptables模式（默认）**

```
Client -> ClusterIP:Port 
       -> iptables DNAT规则 
       -> Pod IP:TargetPort
```

工作原理：
1. kube-proxy监听API Server中Service和Endpoints的变化
2. 为每个Service创建iptables规则
3. 使用随机概率实现负载均衡

**IPVS模式（推荐生产环境）**

```
Client -> ClusterIP:Port 
       -> IPVS Virtual Server 
       -> Pod IP:TargetPort
```

IPVS优势：
- 更高效的数据结构（哈希表 vs 链表）
- 支持更多负载均衡算法（rr、lc、dh、sh、sed、nq）
- 大规模场景下性能更优

启用IPVS模式：

```yaml
# kube-proxy ConfigMap
mode: "ipvs"
ipvs:
  scheduler: "rr"  # 轮询算法
```

##### 3. Endpoints与EndpointSlices

当Service的selector匹配到Pod后，K8s会自动创建Endpoints对象：

```bash
kubectl get endpoints my-service
# 输出示例：
# NAME         ENDPOINTS                         AGE
# my-service   10.244.1.5:8080,10.244.2.8:8080   5m
```

**EndpointSlices**是Endpoints的升级版，解决了大规模集群中Endpoints对象过大的问题：

- 每个EndpointSlice最多包含100个端点
- 支持更细粒度的更新
- 减少API Server和etcd的压力

#### DNS服务发现

K8s内置的CoreDNS为Service提供DNS解析：

```
<service-name>.<namespace>.svc.cluster.local
```

示例：

```bash
# 在Pod内部
curl http://my-service.default.svc.cluster.local:80
# 或简写（同namespace内）
curl http://my-service:80
```

#### Headless Service

当你不需要负载均衡和单一Service IP时，可以创建Headless Service：

```yaml
apiVersion: v1
kind: Service
metadata:
  name: my-headless-service
spec:
  clusterIP: None  # 关键配置
  selector:
    app: my-app
  ports:
    - port: 80
```

特点：
- 不分配ClusterIP
- DNS查询直接返回所有Pod的IP
- 适用于StatefulSet、需要直连Pod的场景

#### 常见问题排查

##### 1. Service无法访问

```bash
# 检查Service是否存在
kubectl get svc my-service

# 检查Endpoints是否正常
kubectl get endpoints my-service

# 检查Pod是否Running且Ready
kubectl get pods -l app=my-app

# 检查selector是否匹配
kubectl describe svc my-service
```

##### 2. 端口配置问题

```yaml
spec:
  ports:
    - port: 80        # Service暴露的端口
      targetPort: 8080 # Pod监听的端口
      nodePort: 30080  # NodePort类型时节点端口
```

##### 3. kube-proxy日志

```bash
# 查看kube-proxy日志
kubectl logs -n kube-system -l k8s-app=kube-proxy
```

#### 生产环境最佳实践

1. **使用IPVS模式**：大规模集群建议切换到IPVS模式
2. **合理设置Session Affinity**：需要会话保持时配置`sessionAffinity: ClientIP`
3. **使用Ingress暴露HTTP服务**：比NodePort/LoadBalancer更灵活
4. **监控Service指标**：关注连接数、延迟、错误率
5. **使用Network Policy**：限制Service的网络访问策略

#### 总结

理解K8s Service网络模型的关键点：

1. Service是对一组Pod的抽象，提供稳定的访问入口
2. kube-proxy通过iptables/IPVS实现流量转发
3. CoreDNS提供服务发现能力
4. 不同类型的Service适用于不同场景

掌握这些知识，能帮助你更好地设计K8s应用架构，快速定位网络问题！

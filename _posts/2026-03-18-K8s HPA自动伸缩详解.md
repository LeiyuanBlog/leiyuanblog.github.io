## K8s HPA自动伸缩详解

#### 为什么需要自动伸缩

1. 在前面的文章中,我们学习了Pod、Service、Deployment、Ingress等核心资源的管理
2. 但在生产环境中,应用的流量是动态变化的--**高峰期需要更多副本,低谷期减少副本以节省资源**
3. 手动调整副本数既不及时也不现实,Kubernetes提供了HPA(Horizontal Pod Autoscaler)来自动根据负载调整Pod数量

#### 什么是HPA

HPA(Horizontal Pod Autoscaler)是Kubernetes的自动伸缩控制器,它:

- **监控**Pod的资源使用率(CPU、内存)或自定义指标
- **计算**期望的副本数
- **调整**Deployment/StatefulSet/ReplicaSet的副本数
- **周期性**执行(默认每15秒检查一次)

**核心思想**:根据实际负载自动水平扩缩容,让应用始终以合适的规模运行

#### HPA工作原理

##### 整体架构

```
                    Metrics Server
                         |
                    收集Pod指标
                         |
HPA Controller  <---  查询指标  --->  计算期望副本数
      |
      v
调整Deployment.spec.replicas
      |
      v
Deployment Controller创建/删除Pod
```

##### 核心计算公式

```
期望副本数 = ceil(当前副本数 × (当前指标值 / 目标指标值))
```

**举例**:

- 当前副本数: 3
- 当前CPU使用率: 90%
- 目标CPU使用率: 50%
- 期望副本数 = ceil(3 × (90 / 50)) = ceil(5.4) = 6

##### 伸缩策略

| 场景 | 行为 | 说明 |
|------|------|------|
| 指标超过目标值 | 扩容(Scale Up) | 快速响应,避免服务过载 |
| 指标低于目标值 | 缩容(Scale Down) | 缓慢收缩,默认稳定窗口5分钟 |
| 指标在目标值附近 | 保持不变 | 容忍度默认10%,避免频繁抖动 |

#### 前置条件:Metrics Server

HPA依赖Metrics Server来获取Pod的资源指标,确保集群已安装:

```bash
# 检查Metrics Server是否运行
kubectl get pods -n kube-system | grep metrics-server

# 如果未安装,使用以下命令安装
kubectl apply -f https://github.com/kubernetes-sigs/metrics-server/releases/latest/download/components.yaml

# 验证是否正常工作
kubectl top nodes
kubectl top pods -n default
```

> 注意:如果`kubectl top`返回错误,可能需要在Metrics Server的Deployment中添加`--kubelet-insecure-tls`参数(仅测试环境)

#### 基于CPU的HPA

##### 准备示例应用

首先部署一个有资源请求的应用(HPA必须依赖resources.requests):

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: web-app
  namespace: default
spec:
  replicas: 2
  selector:
    matchLabels:
      app: web-app
  template:
    metadata:
      labels:
        app: web-app
    spec:
      containers:
        - name: web
          image: nginx:1.24
          ports:
            - containerPort: 80
          resources:
            requests:
              cpu: 100m        # HPA计算的基准,必须设置!
              memory: 128Mi
            limits:
              cpu: 200m
              memory: 256Mi
---
apiVersion: v1
kind: Service
metadata:
  name: web-app-svc
spec:
  selector:
    app: web-app
  ports:
    - port: 80
      targetPort: 80
```

> **重要**:如果Pod没有设置`resources.requests`,HPA将无法计算CPU使用率百分比!

##### 创建HPA(命令行方式)

```bash
kubectl autoscale deployment web-app \
  --cpu-percent=50 \
  --min=2 \
  --max=10
```

##### 创建HPA(YAML方式)

```yaml
apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata:
  name: web-app-hpa
  namespace: default
spec:
  scaleTargetRef:
    apiVersion: apps/v1
    kind: Deployment
    name: web-app
  minReplicas: 2
  maxReplicas: 10
  metrics:
    - type: Resource
      resource:
        name: cpu
        target:
          type: Utilization
          averageUtilization: 50    # 目标CPU使用率50%
```

##### 字段详解

| 字段 | 说明 | 注意事项 |
|------|------|----------|
| scaleTargetRef | 伸缩目标(Deployment/StatefulSet) | 必须存在且有replicas字段 |
| minReplicas | 最小副本数 | 不能为0(除非启用缩容到0功能) |
| maxReplicas | 最大副本数 | 根据集群资源合理设置 |
| metrics | 伸缩指标列表 | 可配置多个指标 |
| averageUtilization | 目标使用率百分比 | 基于requests计算 |

#### 基于内存的HPA

```yaml
apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata:
  name: web-app-memory-hpa
spec:
  scaleTargetRef:
    apiVersion: apps/v1
    kind: Deployment
    name: web-app
  minReplicas: 2
  maxReplicas: 10
  metrics:
    - type: Resource
      resource:
        name: memory
        target:
          type: Utilization
          averageUtilization: 70    # 目标内存使用率70%
```

> **注意**:内存型HPA在缩容时效果可能不如CPU,因为很多应用释放内存较慢(如JVM),需要特别关注

#### 多指标HPA

可以同时基于CPU和内存进行伸缩,HPA会取计算结果中**最大的副本数**:

```yaml
apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata:
  name: web-app-multi-hpa
spec:
  scaleTargetRef:
    apiVersion: apps/v1
    kind: Deployment
    name: web-app
  minReplicas: 2
  maxReplicas: 15
  metrics:
    - type: Resource
      resource:
        name: cpu
        target:
          type: Utilization
          averageUtilization: 50
    - type: Resource
      resource:
        name: memory
        target:
          type: Utilization
          averageUtilization: 70
```

#### 伸缩行为控制(Behavior)

Kubernetes v1.23+支持通过`behavior`字段精细控制伸缩速率:

```yaml
apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata:
  name: web-app-controlled-hpa
spec:
  scaleTargetRef:
    apiVersion: apps/v1
    kind: Deployment
    name: web-app
  minReplicas: 2
  maxReplicas: 20
  metrics:
    - type: Resource
      resource:
        name: cpu
        target:
          type: Utilization
          averageUtilization: 50
  behavior:
    scaleUp:
      stabilizationWindowSeconds: 30     # 扩容稳定窗口30秒
      policies:
        - type: Percent
          value: 100                      # 每次最多扩容当前副本数的100%
          periodSeconds: 60
        - type: Pods
          value: 5                        # 或每次最多扩容5个Pod
          periodSeconds: 60
      selectPolicy: Max                   # 取两个策略中较大值
    scaleDown:
      stabilizationWindowSeconds: 300    # 缩容稳定窗口5分钟
      policies:
        - type: Percent
          value: 10                       # 每次最多缩容10%
          periodSeconds: 60
      selectPolicy: Min                   # 保守缩容
```

##### Behavior字段详解

| 字段 | 说明 | 默认值 |
|------|------|--------|
| stabilizationWindowSeconds | 稳定窗口,防止指标波动导致频繁伸缩 | 扩容:0秒 / 缩容:300秒 |
| policies.type | 策略类型:Pods(绝对数)或Percent(百分比) | - |
| policies.value | 每个周期允许变化的数量/百分比 | - |
| policies.periodSeconds | 策略评估周期 | - |
| selectPolicy | 多策略时取Max/Min/Disabled | Max |

##### 常见场景配置

**快速扩容,慢速缩容(推荐)**:

```yaml
behavior:
  scaleUp:
    stabilizationWindowSeconds: 0      # 立即扩容
    policies:
      - type: Percent
        value: 100
        periodSeconds: 15
  scaleDown:
    stabilizationWindowSeconds: 600    # 10分钟稳定窗口
    policies:
      - type: Percent
        value: 5
        periodSeconds: 60
```

**禁止缩容(只扩不缩)**:

```yaml
behavior:
  scaleDown:
    selectPolicy: Disabled
```

#### 自定义指标HPA

除了CPU和内存,还可以基于自定义指标(如QPS、队列长度)进行伸缩:

##### 前置条件

需要安装自定义指标适配器,常见选择:

- **Prometheus Adapter**:最流行,将Prometheus指标暴露为Kubernetes自定义指标
- **KEDA**:事件驱动的自动伸缩,支持更多指标源

##### 基于Pod自定义指标

```yaml
apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata:
  name: web-app-custom-hpa
spec:
  scaleTargetRef:
    apiVersion: apps/v1
    kind: Deployment
    name: web-app
  minReplicas: 2
  maxReplicas: 20
  metrics:
    - type: Pods
      pods:
        metric:
          name: http_requests_per_second    # 自定义指标名
        target:
          type: AverageValue
          averageValue: "100"               # 每个Pod目标100 QPS
```

##### 基于外部指标(如消息队列长度)

```yaml
apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata:
  name: worker-hpa
spec:
  scaleTargetRef:
    apiVersion: apps/v1
    kind: Deployment
    name: queue-worker
  minReplicas: 1
  maxReplicas: 30
  metrics:
    - type: External
      external:
        metric:
          name: rabbitmq_queue_messages
          selector:
            matchLabels:
              queue: task-queue
        target:
          type: AverageValue
          averageValue: "10"               # 每个Pod处理10条消息
```

#### 实战:压力测试验证HPA

##### 步骤1:部署应用和HPA

```bash
# 部署应用
kubectl apply -f web-app-deployment.yaml

# 创建HPA
kubectl autoscale deployment web-app --cpu-percent=50 --min=2 --max=10

# 查看初始状态
kubectl get hpa
```

##### 步骤2:制造压力

```bash
# 启动一个临时Pod进行压测
kubectl run load-generator --image=busybox:1.36 --restart=Never -- \
  /bin/sh -c "while true; do wget -q -O- http://web-app-svc; done"
```

##### 步骤3:观察伸缩过程

```bash
# 持续观察HPA状态
kubectl get hpa -w

# 输出示例:
# NAME          REFERENCE            TARGETS    MINPODS   MAXPODS   REPLICAS
# web-app-hpa   Deployment/web-app   12%/50%    2         10        2
# web-app-hpa   Deployment/web-app   68%/50%    2         10        2
# web-app-hpa   Deployment/web-app   95%/50%    2         10        4
# web-app-hpa   Deployment/web-app   71%/50%    2         10        6
# web-app-hpa   Deployment/web-app   48%/50%    2         10        6

# 观察Pod数量变化
kubectl get pods -l app=web-app -w
```

##### 步骤4:停止压力,观察缩容

```bash
# 删除压测Pod
kubectl delete pod load-generator

# 等待5分钟(默认缩容稳定窗口),观察副本数逐渐减少
kubectl get hpa -w
```

```bash
# 查看HPA列表和状态
```

#### 常见问题排查

##### 问题1:HPA显示TARGETS为\<unknown\>

```
NAME          REFERENCE            TARGETS           MINPODS   MAXPODS   REPLICAS
web-app-hpa   Deployment/web-app   <unknown>/50%     2         10        2
```

排查步骤:

```bash
# 1. 检查Metrics Server是否正常
kubectl get pods -n kube-system | grep metrics-server
kubectl top pods

# 2. 检查Pod是否设置了resources.requests
kubectl get pod <pod-name> -o yaml | grep -A5 resources

# 3. 检查HPA事件
kubectl describe hpa web-app-hpa
```

常见原因:
- Metrics Server未安装或未正常运行
- Pod未设置`resources.requests`
- Pod刚启动,指标还未采集到(等1-2分钟)

##### 问题2:HPA不扩容

```bash
# 1. 检查HPA条件
kubectl describe hpa web-app-hpa
# 查看Conditions部分,是否有ScalingLimited

# 2. 确认已达到maxReplicas
kubectl get hpa

# 3. 检查集群资源是否充足
kubectl describe nodes | grep -A5 "Allocated resources"
```

##### 问题3:HPA频繁抖动(忽上忽下)

通过调整behavior解决:

```yaml
behavior:
  scaleUp:
    stabilizationWindowSeconds: 120    # 增加扩容稳定窗口
  scaleDown:
    stabilizationWindowSeconds: 600    # 增加缩容稳定窗口
```

#### 最佳实践

1. **务必设置resources.requests**,这是HPA计算的基础,没有requests就没有百分比
2. **合理设置min和max**,min不要太低(避免流量突增时响应不及时),max不要超过集群承载能力
3. **优先使用CPU指标**,CPU对负载的反应最直接,内存通常作为辅助指标
4. **配置behavior控制伸缩速率**,推荐"快扩慢缩"策略,避免频繁伸缩
5. **不要与kubectl scale混用**,手动设置replicas会与HPA冲突
6. **配合PDB(PodDisruptionBudget)使用**,确保缩容时不影响服务可用性
7. **在生产环境先观察再调优**,初始可以设置较保守的参数,观察一段时间后调整
8. **考虑使用VPA配合HPA**,VPA(垂直伸缩)调整单Pod资源,HPA调整Pod数量,二者互补

#### 总结

| 概念 | 说明 | 关键配置 |
|------|------|----------|
| HPA | 根据指标自动调整Pod副本数 | metrics + min/maxReplicas |
| Metrics Server | 提供Pod资源指标 | 集群级组件,必须安装 |
| CPU指标 | 基于CPU使用率伸缩 | 依赖resources.requests |
| 内存指标 | 基于内存使用率伸缩 | 注意应用内存释放特性 |
| 自定义指标 | 基于业务指标伸缩 | 需要Prometheus Adapter等 |
| Behavior | 精细控制伸缩速率 | stabilizationWindow + policies |

HPA是Kubernetes弹性伸缩的核心能力,掌握了HPA就掌握了让应用**自动适应负载变化**的能力。配合合理的指标选择和伸缩策略,可以在保证服务质量的同时最大化资源利用率。

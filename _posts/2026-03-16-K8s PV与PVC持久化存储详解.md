## K8s PV与PVC持久化存储详解

#### 前文回顾

1. 在之前的系列文章中，我们学习了Pod、Service、ConfigMap、Secret、Deployment以及Ingress等核心资源。
2. 但有一个非常关键的问题还没有解决——**容器中的数据是临时的**，Pod重启后数据就会丢失。
3. 对于数据库、日志、配置文件等有状态数据，我们需要一套可靠的持久化存储方案。今天就来深入学习Kubernetes中的PV与PVC。

#### 为什么需要持久化存储

默认情况下，容器内的文件系统是临时的（ephemeral）：

- Pod被删除或重启后，容器中写入的数据**全部丢失**
- 同一Pod中多个容器之间无法直接共享文件
- 数据和容器生命周期绑定，不利于有状态应用

虽然可以使用`hostPath`将宿主机目录挂载到容器内，但这样会导致Pod和特定节点绑定，违背了Kubernetes灵活调度的设计理念。

**PV和PVC的出现，就是为了将存储和计算解耦。**

#### 核心概念

##### PersistentVolume (PV)

PV是集群中的一块存储资源，由**管理员预先创建**或通过StorageClass动态创建。它的特点：

- 独立于Pod的生命周期存在
- 是集群级别的资源（不属于任何Namespace）
- 代表实际的存储后端（NFS、Ceph、云盘等）

##### PersistentVolumeClaim (PVC)

PVC是用户对存储的**请求声明**，类似Pod消耗Node资源，PVC消耗PV资源。它的特点：

- 是Namespace级别的资源
- 用户只需声明"我需要多大、什么类型的存储"
- Kubernetes自动匹配合适的PV进行绑定

##### PV与PVC的关系

```
管理员/StorageClass                    用户/开发者
      │                                    │
   创建 PV ──bindding──→ PVC ──mount──→ Pod
  (实际存储)            (存储请求)       (使用存储)
```

**这种分离设计的好处**：开发者不需要关心底层存储细节，只需声明需求；运维人员负责管理实际的存储基础设施。

#### PV的定义与配置

##### 基础PV示例（NFS）

```yaml
apiVersion: v1
kind: PersistentVolume
metadata:
  name: my-nfs-pv
  labels:
    type: nfs
spec:
  capacity:
    storage: 10Gi
  accessModes:
    - ReadWriteMany
  persistentVolumeReclaimPolicy: Retain
  nfs:
    server: 192.168.1.100
    path: /data/k8s-pv
```

##### 关键字段解析

**capacity（容量）**

```yaml
capacity:
  storage: 10Gi   # 存储容量
```

**accessModes（访问模式）**

| 模式 | 缩写 | 说明 |
|------|------|------|
| ReadWriteOnce | RWO | 单节点读写 |
| ReadOnlyMany | ROX | 多节点只读 |
| ReadWriteMany | RWX | 多节点读写 |
| ReadWriteOncePod | RWOP | 单Pod读写（K8s 1.22+） |

> ⚠️ 不同存储后端支持的访问模式不同，例如大多数云盘只支持RWO，NFS支持RWX。

**persistentVolumeReclaimPolicy（回收策略）**

| 策略 | 说明 |
|------|------|
| Retain | PVC删除后，PV保留数据，需手动回收 |
| Delete | PVC删除后，PV和底层存储一并删除 |
| Recycle | (已废弃) 清空数据后重新可用 |

**PV的状态流转**

```
Available → Bound → Released → Available/Failed
  (可用)    (已绑定)  (已释放)
```

#### PVC的定义与配置

##### 基础PVC示例

```yaml
apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  name: my-pvc
  namespace: default
spec:
  accessModes:
    - ReadWriteMany
  resources:
    requests:
      storage: 5Gi
  selector:
    matchLabels:
      type: nfs
```

##### PV与PVC的匹配规则

Kubernetes按以下条件匹配PV和PVC：

1. **accessModes**：PV的访问模式必须包含PVC请求的模式
2. **capacity**：PV的容量必须 >= PVC请求的容量
3. **selector**：如果PVC指定了selector，则PV的labels必须匹配
4. **storageClassName**：两者必须一致（或都不指定）

#### 在Pod中使用PVC

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: my-app
spec:
  containers:
    - name: app
      image: nginx:1.24
      volumeMounts:
        - name: data-volume
          mountPath: /usr/share/nginx/html
  volumes:
    - name: data-volume
      persistentVolumeClaim:
        claimName: my-pvc
```

#### StorageClass与动态供给

手动创建PV在规模较大时非常繁琐。**StorageClass**实现了PV的动态创建。

##### StorageClass定义

```yaml
apiVersion: storage.k8s.io/v1
kind: StorageClass
metadata:
  name: fast-ssd
provisioner: kubernetes.io/aws-ebs   # 存储供应器
parameters:
  type: gp3
  fsType: ext4
reclaimPolicy: Delete
allowVolumeExpansion: true            # 允许扩容
volumeBindingMode: WaitForFirstConsumer  # 延迟绑定
```

##### 使用StorageClass的PVC

```yaml
apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  name: dynamic-pvc
spec:
  storageClassName: fast-ssd    # 指定StorageClass
  accessModes:
    - ReadWriteOnce
  resources:
    requests:
      storage: 20Gi
```

当PVC创建后，StorageClass会**自动创建**一个满足要求的PV并完成绑定，无需管理员手动操作。

##### 常见Provisioner

| Provisioner | 存储类型 |
|-------------|---------|
| kubernetes.io/aws-ebs | AWS EBS云盘 |
| kubernetes.io/gce-pd | GCP持久磁盘 |
| kubernetes.io/azure-disk | Azure磁盘 |
| nfs-subdir-external-provisioner | NFS动态供给 |
| rook-ceph.rbd.csi.ceph.com | Ceph RBD |

#### 实战：NFS + 动态供给

下面演示一个完整的NFS动态供给方案。

##### 1. 安装NFS Provisioner（使用Helm）

```bash
helm repo add nfs-subdir-external-provisioner https://kubernetes-sigs.github.io/nfs-subdir-external-provisioner/

helm install nfs-provisioner nfs-subdir-external-provisioner/nfs-subdir-external-provisioner \
  --set nfs.server=192.168.1.100 \
  --set nfs.path=/data/k8s-dynamic \
  --set storageClass.name=nfs-dynamic \
  --set storageClass.defaultClass=true
```

##### 2. 创建PVC（自动获得PV）

```yaml
apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  name: app-data
spec:
  storageClassName: nfs-dynamic
  accessModes:
    - ReadWriteMany
  resources:
    requests:
      storage: 1Gi
```

##### 3. 部署使用该存储的应用

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: web-app
spec:
  replicas: 3
  selector:
    matchLabels:
      app: web
  template:
    metadata:
      labels:
        app: web
    spec:
      containers:
        - name: nginx
          image: nginx:1.24
          volumeMounts:
            - name: web-data
              mountPath: /usr/share/nginx/html
      volumes:
        - name: web-data
          persistentVolumeClaim:
            claimName: app-data
```

三个副本共享同一份NFS存储，任何一个Pod写入的数据，其他Pod都能读取。

#### 常用运维命令

```bash
# 查看PV
kubectl get pv
kubectl describe pv my-nfs-pv

# 查看PVC
kubectl get pvc -A
kubectl describe pvc my-pvc

# 查看StorageClass
kubectl get sc

# 查看PV和PVC的绑定关系
kubectl get pv -o custom-columns=NAME:.metadata.name,CAPACITY:.spec.capacity.storage,STATUS:.status.phase,CLAIM:.spec.claimRef.name

# 扩容PVC（需StorageClass支持）
kubectl patch pvc my-pvc -p '{"spec":{"resources":{"requests":{"storage":"20Gi"}}}}'
```

#### 常见问题排查

##### PVC一直处于Pending状态

```bash
kubectl describe pvc my-pvc
```

常见原因：
- **没有匹配的PV**：检查容量、accessModes、storageClassName是否匹配
- **StorageClass不存在**：`kubectl get sc` 确认
- **Provisioner未就绪**：检查provisioner Pod是否正常运行
- **volumeBindingMode为WaitForFirstConsumer**：需要有Pod引用该PVC后才会绑定

##### PV状态为Released无法复用

PVC删除后PV变为Released状态，不会自动变为Available。处理方法：

```bash
# 方法1：删除claimRef（保留数据）
kubectl patch pv my-pv -p '{"spec":{"claimRef":null}}'

# 方法2：删除PV重建
kubectl delete pv my-pv
# 重新创建PV yaml
```

##### 扩容后Pod内看不到新容量

某些存储类型需要重启Pod才能生效：

```bash
kubectl rollout restart deployment my-app
```

#### 最佳实践

1. **生产环境使用StorageClass动态供给**，避免手动管理大量PV
2. **重要数据使用Retain回收策略**，防止误删数据
3. **合理选择accessModes**：非必要不用RWX，RWO性能通常更好
4. **启用allowVolumeExpansion**，方便后期扩容
5. **使用volumeBindingMode: WaitForFirstConsumer**，让PV在Pod调度时再绑定，避免跨区问题
6. **为不同场景创建不同的StorageClass**（如fast-ssd、standard-hdd）
7. **定期清理Released状态的PV**，避免存储资源浪费

#### 总结

| 概念 | 作用 | 级别 |
|------|------|------|
| PV | 实际存储资源 | 集群级 |
| PVC | 存储请求声明 | Namespace级 |
| StorageClass | 动态供给模板 | 集群级 |

PV和PVC将存储的**供给方**和**使用方**解耦，StorageClass进一步实现了自动化。理解了这三者的关系，Kubernetes的存储体系就通了大半。

## K8s RBAC权限管理详解

#### 为什么要学

1. 前面的文章中，我们学习了Pod、Service、ConfigMap、Secret、Deployment、Ingress以及PV/PVC等核心资源
2. 在生产环境中，集群通常由多个团队共享使用——**谁能做什么，必须有明确的边界**
3. 如果每个人都拥有集群管理员权限，一个误操作就可能导致全集群宕机。Kubernetes通过RBAC机制实现精细化的权限控制

#### 没有权限管理会怎样

想象一个没有门禁的办公楼：

- 任何人都能进入任何房间，删除任何文件
- 实习生可以误删生产环境的Deployment
- 开发人员可以查看其他团队的Secret（数据库密码、API密钥）
- 无法追溯"谁做了什么"

**RBAC就是Kubernetes的门禁系统，确保每个人只能做被授权的事情**

#### 核心概念

##### Subject（主体）

Subject是权限的承载者，即"谁"要访问资源，Kubernetes中有三种主体：

| 类型 | 说明 | 使用场景 |
|------|------|----------|
| User | 外部用户（由证书/OIDC等认证） | 开发人员、运维人员 |
| Group | 用户组 | 按团队批量授权 |
| ServiceAccount | Pod内的服务账号 | 应用程序访问API Server |

> 注意：Kubernetes没有"用户"资源对象，User是通过外部认证系统（证书CN字段、OIDC等）识别的

##### Role / ClusterRole（角色）

角色定义了**一组权限规则**，即"能做什么"：

- **Role**：命名空间级别，只在指定Namespace内生效
- **ClusterRole**：集群级别，可以管理集群范围的资源（如Node、PV）或跨命名空间使用

##### RoleBinding / ClusterRoleBinding（角色绑定）

角色绑定将**主体和角色关联**起来，即"谁能做什么"：

- **RoleBinding**：在某个Namespace内，将Role或ClusterRole绑定给Subject
- **ClusterRoleBinding**：在整个集群范围内，将ClusterRole绑定给Subject

##### 整体关系

```
Subject（谁）  ←bindding→  RoleBinding  ←reference→  Role（能做什么）
    |                          |                         |
  User              Namespace级别绑定            Namespace级别权限
  Group
  ServiceAccount

Subject（谁）  ←bindding→  ClusterRoleBinding  ←reference→  ClusterRole（能做什么）
    |                          |                                |
  User                集群级别绑定                       集群级别权限
  Group
  ServiceAccount
```

**一句话记忆**：RBAC = 谁(Subject) + 能做什么(Role) + 在哪绑定(Binding)

#### Role与ClusterRole

##### 创建Role（命名空间级别）

```yaml
apiVersion: rbac.authorization.k8s.io/v1
kind: Role
metadata:
  name: pod-reader
  namespace: dev
rules:
  - apiGroups: [""]          # 核心API组，用空字符串表示
    resources: ["pods"]       # 资源类型
    verbs: ["get", "list", "watch"]  # 允许的操作
```

##### 创建ClusterRole（集群级别）

```yaml
apiVersion: rbac.authorization.k8s.io/v1
kind: ClusterRole
metadata:
  name: node-viewer
rules:
  - apiGroups: [""]
    resources: ["nodes"]
    verbs: ["get", "list", "watch"]
  - apiGroups: [""]
    resources: ["persistentvolumes"]
    verbs: ["get", "list"]
```

##### rules字段详解

**apiGroups（API组）**

| API组 | 包含资源 | 写法 |
|-------|---------|------|
| 核心组 | Pod、Service、ConfigMap、Secret、PV、PVC等 | `""` |
| apps | Deployment、StatefulSet、DaemonSet | `"apps"` |
| batch | Job、CronJob | `"batch"` |
| networking.k8s.io | Ingress、NetworkPolicy | `"networking.k8s.io"` |
| rbac.authorization.k8s.io | Role、ClusterRole、Binding | `"rbac.authorization.k8s.io"` |

> 提示：不确定某个资源属于哪个API组？使用 `kubectl api-resources` 查看

**verbs（操作动词）**

| 动词 | 说明 | 对应kubectl操作 |
|------|------|----------------|
| get | 获取单个资源 | kubectl get pod xxx |
| list | 列出资源 | kubectl get pods |
| watch | 监听变更 | kubectl get pods -w |
| create | 创建资源 | kubectl apply/create |
| update | 更新资源 | kubectl apply/edit |
| patch | 部分更新 | kubectl patch |
| delete | 删除资源 | kubectl delete |
| deletecollection | 批量删除 | kubectl delete pods --all |

**resources（资源）与子资源**

```yaml
rules:
  - apiGroups: [""]
    resources: ["pods"]           # Pod资源
    verbs: ["get", "list"]
  - apiGroups: [""]
    resources: ["pods/log"]       # Pod的日志（子资源）
    verbs: ["get"]
  - apiGroups: [""]
    resources: ["pods/exec"]      # Pod的exec（子资源）
    verbs: ["create"]
```

**resourceNames（限定具体资源名称）**

```yaml
rules:
  - apiGroups: [""]
    resources: ["configmaps"]
    resourceNames: ["app-config", "nginx-config"]  # 只能操作这两个ConfigMap
    verbs: ["get", "update"]
```

#### RoleBinding与ClusterRoleBinding

##### 创建RoleBinding

```yaml
apiVersion: rbac.authorization.k8s.io/v1
kind: RoleBinding
metadata:
  name: read-pods-binding
  namespace: dev
subjects:
  - kind: User
    name: zhangsan
    apiGroup: rbac.authorization.k8s.io
  - kind: ServiceAccount
    name: my-app-sa
    namespace: dev
roleRef:
  kind: Role
  name: pod-reader
  apiGroup: rbac.authorization.k8s.io
```

上面的配置将`dev`命名空间中的`pod-reader`角色绑定给用户`zhangsan`和ServiceAccount`my-app-sa`

##### 创建ClusterRoleBinding

```yaml
apiVersion: rbac.authorization.k8s.io/v1
kind: ClusterRoleBinding
metadata:
  name: node-viewer-binding
subjects:
  - kind: Group
    name: ops-team
    apiGroup: rbac.authorization.k8s.io
roleRef:
  kind: ClusterRole
  name: node-viewer
  apiGroup: rbac.authorization.k8s.io
```

##### 重要：RoleBinding引用ClusterRole

RoleBinding可以引用ClusterRole，但权限**仅限于RoleBinding所在的Namespace**：

```yaml
apiVersion: rbac.authorization.k8s.io/v1
kind: RoleBinding
metadata:
  name: admin-in-dev
  namespace: dev
subjects:
  - kind: User
    name: lisi
    apiGroup: rbac.authorization.k8s.io
roleRef:
  kind: ClusterRole
  name: admin            # 引用内置的admin ClusterRole
  apiGroup: rbac.authorization.k8s.io
```

这样`lisi`在`dev`命名空间拥有admin权限，但在其他命名空间没有任何权限。这是一种常用的复用模式

#### ServiceAccount实战

ServiceAccount是Pod内应用访问API Server的身份凭证，也是RBAC最常用的场景之一

##### 创建ServiceAccount

```yaml
apiVersion: v1
kind: ServiceAccount
metadata:
  name: cicd-sa
  namespace: dev
```

##### 为ServiceAccount绑定权限

```yaml
apiVersion: rbac.authorization.k8s.io/v1
kind: Role
metadata:
  name: deployment-manager
  namespace: dev
rules:
  - apiGroups: ["apps"]
    resources: ["deployments"]
    verbs: ["get", "list", "create", "update", "patch"]
  - apiGroups: [""]
    resources: ["pods"]
    verbs: ["get", "list", "watch"]
---
apiVersion: rbac.authorization.k8s.io/v1
kind: RoleBinding
metadata:
  name: cicd-deploy-binding
  namespace: dev
subjects:
  - kind: ServiceAccount
    name: cicd-sa
    namespace: dev
roleRef:
  kind: Role
  name: deployment-manager
  apiGroup: rbac.authorization.k8s.io
```

##### 在Pod中使用ServiceAccount

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: cicd-runner
  namespace: dev
spec:
  serviceAccountName: cicd-sa    # 指定ServiceAccount
  containers:
    - name: runner
      image: bitnami/kubectl:1.28
      command: ["sleep", "infinity"]
```

进入该Pod后，只能执行被授权的操作：

```bash
# 可以执行（被授权）
kubectl get deployments -n dev
kubectl get pods -n dev

# 不能执行（未授权，返回403 Forbidden）
kubectl get secrets -n dev
kubectl get pods -n production
```

#### 内置ClusterRole

Kubernetes预置了几个常用的ClusterRole：

| ClusterRole | 权限范围 | 适用场景 |
|-------------|---------|---------|
| cluster-admin | 所有资源所有操作 | 集群管理员（谨慎使用） |
| admin | 命名空间内几乎所有资源 | 项目管理员 |
| edit | 读写大部分资源（不含Role/RoleBinding） | 开发人员 |
| view | 只读大部分资源（不含Secret） | 只读查看 |

```bash
# 快速给用户在某个命名空间赋予edit权限
kubectl create rolebinding dev-edit \
  --clusterrole=edit \
  --user=zhangsan \
  --namespace=dev
```

#### 实战：多团队权限隔离

假设有三个团队共享一个集群：

##### 1. 创建命名空间

```bash
kubectl create namespace team-frontend
kubectl create namespace team-backend
kubectl create namespace team-data
```

##### 2. 为每个团队创建ServiceAccount和权限

```yaml
# team-backend为例
apiVersion: v1
kind: ServiceAccount
metadata:
  name: backend-dev
  namespace: team-backend
---
apiVersion: rbac.authorization.k8s.io/v1
kind: RoleBinding
metadata:
  name: backend-edit-binding
  namespace: team-backend
subjects:
  - kind: ServiceAccount
    name: backend-dev
    namespace: team-backend
roleRef:
  kind: ClusterRole
  name: edit
  apiGroup: rbac.authorization.k8s.io
```

##### 3. 运维团队跨命名空间只读

```yaml
apiVersion: rbac.authorization.k8s.io/v1
kind: ClusterRoleBinding
metadata:
  name: ops-global-view
subjects:
  - kind: Group
    name: ops-team
    apiGroup: rbac.authorization.k8s.io
roleRef:
  kind: ClusterRole
  name: view
  apiGroup: rbac.authorization.k8s.io
```

这样每个团队只能管理自己命名空间的资源，运维团队可以全局只读查看

#### 常用命令

```bash
# 查看当前用户权限
kubectl auth can-i create deployments --namespace=dev
kubectl auth can-i '*' '*'    # 是否是集群管理员

# 以某个用户身份检查权限
kubectl auth can-i list pods --namespace=dev --as=zhangsan
kubectl auth can-i list pods --namespace=dev --as=system:serviceaccount:dev:cicd-sa

# 查看Role和ClusterRole
kubectl get roles -n dev
kubectl get clusterroles | grep -v system:

# 查看绑定关系
kubectl get rolebindings -n dev
kubectl get clusterrolebindings

# 查看Role详情
kubectl describe role pod-reader -n dev
kubectl describe clusterrole edit

# 快速创建绑定（命令行方式）
kubectl create rolebinding my-binding \
  --role=pod-reader \
  --user=zhangsan \
  --namespace=dev

kubectl create clusterrolebinding my-cluster-binding \
  --clusterrole=view \
  --group=dev-team
```

#### 常见问题

##### 权限不足报错：Forbidden

```
Error from server (Forbidden): pods is forbidden: User "zhangsan" cannot list resource "pods" in API group "" in the namespace "production"
```

排查步骤：

```bash
# 1. 确认用户身份
kubectl auth can-i list pods -n production --as=zhangsan

# 2. 检查是否有对应的RoleBinding
kubectl get rolebindings -n production -o wide

# 3. 查看绑定的Role包含哪些权限
kubectl describe role <role-name> -n production
```

##### ServiceAccount Token问题（K8s 1.24+）

从Kubernetes 1.24开始，不再自动为ServiceAccount创建永久Token Secret。获取Token的方式：

```bash
# 方式1：创建有时限的Token（推荐）
kubectl create token cicd-sa -n dev --duration=24h

# 方式2：手动创建Secret（长期Token）
cat <<EOF | kubectl apply -f -
apiVersion: v1
kind: Secret
metadata:
  name: cicd-sa-token
  namespace: dev
  annotations:
    kubernetes.io/service-account.name: cicd-sa
type: kubernetes.io/service-account-token
EOF
```

##### Role和ClusterRole的选择

- 资源是否有Namespace（如Pod、Deployment）→ 可以用Role
- 资源是集群级别的（如Node、PV、Namespace本身）→ 必须用ClusterRole
- 需要跨Namespace统一定义权限模板 → ClusterRole + RoleBinding复用

#### 最佳实践

1. **遵循最小权限原则**，只授予完成工作所需的最少权限
2. **避免使用cluster-admin**，除非真的需要管理整个集群
3. **优先使用内置ClusterRole**（view/edit/admin），减少自定义Role的维护成本
4. **使用Group而非User绑定**，方便团队成员变更时统一管理
5. **为每个应用创建独立的ServiceAccount**，不要使用default ServiceAccount
6. **定期审计权限**，使用`kubectl auth can-i --list`检查权限范围
7. **在CI/CD中使用短期Token**（`kubectl create token`），避免长期凭证泄露

#### 总结

| 概念 | 作用 | 作用域 |
|------|------|--------|
| Role | 定义命名空间内的权限规则 | Namespace级 |
| ClusterRole | 定义集群级别的权限规则 | 集群级 |
| RoleBinding | 在命名空间内绑定主体和角色 | Namespace级 |
| ClusterRoleBinding | 在集群范围绑定主体和角色 | 集群级 |
| ServiceAccount | Pod内的服务身份 | Namespace级 |

RBAC是Kubernetes安全体系的基石，核心思想就是**最小权限原则**。通过Role定义"能做什么"，通过Binding定义"谁能做"，通过Namespace实现"在哪做"，三者结合实现精细化的访问控制。
